## 1. 文档作用与执行原则

### 1.1 文档的作用

本规范用于指导执行 agent 从空项目仓库出发，自主设计和实施 DriveServe，完成六条技术主线、六个阶段的工程与实验验收，并为项目所有者提供从零到当前阶段的完整理解和讲解材料。

本规范规定“必须完成什么、用什么证据证明、如何保留过程”。具体算法、文件组织、依赖版本、训练配置、实验调度和代码实现，由 agent 根据实际环境、上游能力、正确性与实验结果选择。

agent 应在适用的工具权限和用户授权范围内自主推进，维护工作状态，并在中断后从真实进度继续。文档本身不会启动远程任务、购买算力或提供 GitHub/服务器凭据。

### 1.2 核心原则

1. **先完成，再完善。** 尽快建立可运行链路；随后尽快形成真实覆盖六条主线的最小完整版本，再逐步深化。
2. **同一套叙事，逐步增加深度。** 阶段 2 起，每个可面试发布版本都必须覆盖六条主线。可以算法朴素、支持范围有限，但必须完成真实实现或实验闭环。
3. **阶段 1 是内部准备。** 仅跑通模型、服务或 benchmark，不能宣称已经完成六条主线。
4. **事实先于措辞。** 实际代码、运行记录和实验决定简历表述；不能为了匹配占位数字而修改数据、挑选有利样本或省略失败。
5. **使用上游与个人贡献分清。** 记录已有能力、复用部分和个人修改。原生功能配置不能冒充自研核心实现。
6. **验收先于完成标记。** 实现、测试、实验、文档与资产留存均达到本阶段要求后，才能标记阶段完成。
7. **负结果也是有效结果。** 正确实现、合理对照和可解释结论可以通过工程验收；只有有证据的正收益才能写成性能提升。
8. **过程可追溯，阶段可回放。** 每项关键决策、实现、实验和结论能够关联；每个已发布阶段能独立获取并重现其核心流程。
9. **讲解累计更新。** 每阶段材料覆盖项目从零到该阶段的全部工作，而不只是这一阶段新增的内容。
10. **不静默缩减要求。** 遇到版本、预算或时间冲突，应记录原因并报告具体选择；不能删除某条主线后宣布完整交付。

### 1.3 规范与技术选择的边界

- 文中“必须”“不得”“验收条件”是交付要求；“建议”“例如”是可调整的实施参考。
- 有更合适的实现方式时，agent 可以自主选择并记录决策，前提是不降低最低交付要求和证据质量。
- 项目所有者后续明确调整的范围、预算或目标应记录为规范变更，并同步更新验收矩阵。
- 第 3 节保留的简历原文是目标叙事，不是已完成清单，也不能替代第 4–10 节的实际验收要求。
- 旧十阶段文档可作为技术背景；若其“收缩某条主线”等建议与本规范冲突，以本六阶段规范为准。

## 2. 项目背景、范围与资源约束

### 2.1 项目目标

面向 AI Infra / 大模型推理优化岗位，构建具有源码修改、推理评测、模型压缩、CUDA 算子实践和部署分析的个人项目。项目所有者应能说明自己做了什么、为什么这样做、证据是什么，以及适用边界。

最终深度暂按“具有一定 Transformer 基础的研三学生约四个月的工作量”规划。该描述用于控制工程与研究深度，不代表必须等待四个月才能发布，也不保证 agent 能在某个固定墙钟时间内完成。

### 2.2 资源背景

| 资源 | 已知条件及处理要求 |
|---|---|
| 人员投入 | 项目所有者每天约 9 小时，可用于开发协作、学习、实验审阅和面试准备 |
| GPU | 2×RTX 4090，可暂时租用约一个月；关机后可能被重新调度，重启时可能无卡，或在平台标注的双卡 24GB/48GB 实例之间迁移；实际硬件、驱动、拓扑和存储以检测为准 |
| 租期 | 按约 30 天的租用日历窗口管理，不保证同一 GPU 连续可用；记录实际可用时段和迁移，不假设四个月内持续有 GPU |
| 其他资源 | CPU、内存、磁盘、网络和持久存储尚待检测；不得据此虚构环境或实验成功 |
| 后续算力 | 未承诺；需要额外付费租用时应提出具体预算与必要性，等待用户决定 |

### 2.3 业务与技术边界

1. 初版可以使用车载场景的结构化决策代理任务，例如道路、障碍物、车辆状态和历史信息输入，输出行为类别、速度区间和约束字段。必须记录任务语义、标签来源与评分规则。
2. 如果仅使用结构化文本与规则数据，应明确其为代理任务；不能把它说成感知—规划—控制闭环、真实车辆部署或安全效果验证。
3. 目标模型默认沿用 Qwen2.5-7B，Draft 默认沿用 Qwen2.5-1.5B。agent 应选择并记录实际变体、revision、tokenizer 和 chat template。更换模型家族或规模会影响叙事，应先说明原因和影响。
4. 不强制改造全部 vLLM 后端、支持全部模型，或搭建 Kubernetes、复杂权限系统和大型前端。优先完成与六条主线直接相关的工程。
5. 基础版可以用不同的、明确标记的实验 profile 分别验证各条主线，不要求所有功能在同一个推理进程中同时开启。阶段 5 负责验证可组合部分和部署边界。
6. 当前 CUDA 主线承诺到独立融合算子、正确性与微基准；端到端接入属于可选深化，不能被默认为基础版必需条件，也不能未实现就声称接入成功。

### 2.4 GPU 时间安排原则

agent 应先检测租期是否已经开始，并给出资源计划。若尚未开租，优先完成本地数据、评分器、回放、依赖与脚本准备；若已经在租期内，不机械等待“准备周”结束。

建议资源窗口如下，仅用于首次排期，不是绕过验收的时间承诺：

| 窗口 | 工作重点 |
|---|---|
| 开租前约 5–7 天，如条件允许 | 阶段 1 中可在 CPU 完成的工作，六条主线的源码与兼容性预检 |
| GPU G1–G3 | 真实服务、环境冻结、主要能力冒烟，完成阶段 1 的实机验收 |
| GPU G4–G14 | 集中完成阶段 2 的六条最小闭环，尽早发布完整基础版 |
| GPU G15–G19 | 阶段 3 的正确性、边界与实验完善 |
| GPU G20–G25 | 阶段 4 的重点深化；实现准备可提前穿插，验收须依序完成 |
| GPU G26–G30 | 保护阶段 5 的组合、部署、最终复测和资产备份窗口 |
| GPU 到期后 | 阶段 6 发布、可在 CPU 完成的复现核查、材料完善与项目所有者学习 |

首次排期应评估是否现实。若六条主线的基础闭环或必要验证超出预算，应尽早报告剩余工作与选择，不能把 mock、未训练模型或未上机的 CUDA 代码标为完成。

G1–G30 是资源预算参考。发生无卡启动或迁移时，按实际可用 GPU 时间和完成情况调整工作顺序，同时保留租期截止约束；停机不能被当作租期自动延长。无卡期间继续数据、源码、CPU 检查和文档等可独立工作，待取得 GPU 后补齐实机验收。

GPU 到期后，影响推理执行路径的代码变更必须重新获得 GPU 回归证据，才能替换对应性能结论。文档更新可以继续，未经验证的核心代码应与已验证发布版分开。

### 2.5 环境固定、迁移与无卡工作的最低要求

**必须达到的效果**：更换实例后，能够依靠持久资产、固定依赖和配置恢复开发及实验；24GB/48GB 资源差异原则上通过配置适配，避免仅因迁移反复修改核心算法。环境可恢复不代表性能数值跨实例保持不变。

1. **确认持久存储。** agent 必须核实平台在关机、换卡和实例迁移时实际保留哪些目录，将源码、环境定义、模型、数据、checkpoint 与实验记录放入确认可保留的存储或另行备份。不能仅因目录位于 `/root` 或系统盘就认定可迁移；记录路径、保留范围及读回检查。
2. **固定且可重建。** 项目使用独立、版本明确的环境，不依赖目标实例预装的默认 PyTorch/CUDA。保存依赖锁定信息、vLLM 源码引用、必要编译配置和安装/重建入口；可迁移的环境本体也放入持久目录。宿主 NVIDIA 驱动不随项目目录迁移，必须单独检查兼容性。不能将复制环境目录作为唯一恢复办法。
3. **资源配置与核心实现分离。** 以双卡各 24GB 环境可运行的基础配置为目标；48GB 下的容量扩展配置单独记录。batch、上下文、KV 预算、并行及训练内存配置可调整；不要求所有最大负载在两种容量下都能运行。无法兼容时记录限制和必要改动，不能承诺任意实例免修改运行。
4. **迁移后先核验再测量。** 检测并记录实际 GPU/显存/拓扑、驱动及项目软件栈，核对依赖和编译产物；必要时重建 CUDA 扩展等二进制，再运行受影响路径的正确性与服务冒烟检查。新环境下的性能结论需重新运行匹配的 baseline 与优化配置，不能直接拿旧环境 baseline 计算新环境收益。
5. **分环境保留证据。** 每次运行关联可辨识的环境记录和配置。旧结果仍属于旧环境；跨环境比较必须明确变量，不把换卡、显存或版本变化归因为算法收益。无 GPU 时可继续独立工作，但 GPU 验证项保持待验收。

具体目录、环境工具、依赖版本和恢复脚本由 agent 选择。S1 须验证环境可按保存的定义恢复或重建；真实迁移发生后补充迁移验证记录。未发生真实迁移时如实标记，不要求为此额外租用实例，也不能声称已经验证所有迁移组合。

## 3. 简历项目描述原文与使用规则

### 3.1 当前目标叙事原文

以下正文保留项目所有者确认的版本。数字是待实测占位，动作是需要兑现的交付目标。

基于 vLLM 部署车载规划模型，针对长上下文、高并发优化推理延迟与 KV Cache，结合模型压缩提升实时性和 GPU 利用率。

- **源码分析与性能诊断：** 针对长上下文、高并发下 P99 升高与 KV Cache 容量不足，分析 Scheduler、Block Manager、KV Cache Manager 及 Attention Backend 相关源码并插桩，分析 Prefix Cache 复用、长短请求排队及 Decode 阶段 KV 访存开销。
- **缓存与调度：** 基于 vLLM Block Manager 实现 **Prefix-aware 冷热分层 Cache**，结合 Prefix 复用次数与 Block 生命周期进行保留与淘汰；引入长度感知调度降低队列等待，**Prefix 命中率提升约 15%，P99 延迟降低约 18%**。
- **自适应推测解码：** 在 vLLM 推测解码中按滑动窗口接受率动态调整 **Draft 长度**；使用 Qwen2.5-7B 教师模型蒸馏 Qwen2.5-1.5B Draft Model，**Token 接受率约 68%，Decode TPOT 降低约 18%**。
- **模型量化：** 在 AWQ 校准中结合车载任务数据与层级敏感性分析，完成 **W4A16 量化**；对比通用/车载校准集及不同 Group Size 下的显存、吞吐和任务指标，**模型显存占用降低约 55%**。
- **CUDA Kernel 融合：** 针对 vLLM 中 **RoPE 与 KV Cache Append** 的执行路径实现融合 CUDA Kernel，完成数值一致性验证与 CUDA Event 微基准测试；相较独立执行的基线，**相关算子总耗时降低约 20%**。
- **性能分析与部署：** 评测 **FlashAttention-2** 的 Prefill 性能，使用 **Nsight Systems** 分析 Prefill/Decode 执行时间线及 Kernel Launch 开销；在 **2×RTX 4090** 上对比单卡、双副本与 Tensor Parallel，形成不同请求长度及并发度下的部署建议。

### 3.2 原文与实际版本的对应规则

- 不为上述百分比设强制达标门槛。真实结果可以更大、更小、无差异或负收益。
- 每阶段另行生成事实版简历；保持六条主题与技术叙事，但具体动词、数字、条件和限制必须与当前证据一致。
- 若未观察到 P99 升高、KV 压力或某项瓶颈，应写分析对象与实际发现，不能将目标问题自动作为已证实事实。
- vLLM 模块名称对应选定版本的实际源码。V1 的 KVCacheManager、BlockPool 等不能为了保留原词而虚构为旧版组件。
- “蒸馏”至少要求发生实际训练并产出可验证的 Draft；教师生成数据的 SFT 可以称为序列级蒸馏，但不能称为未做过的 logit 蒸馏。
- 当前量化叙事不要求改写 AWQ 优化目标。领域校准与有限敏感性分析可以支撑基础版，不强制加入任务损失。
- FA2 必须实际用于所报告的评测；其他后端结果不能改名为 FA2。若选定版本不支持，应解决兼容或报告范围变更。
- 当前 CUDA 叙事不包含端到端 TPOT 降低 7%；不得将旧稿中的该数字带回事实版报告。

## 4. 六条主线的最低实现要求

本节定义阶段 2 的覆盖门槛，并在阶段 3–6 持续有效。覆盖不等于全部获得正收益，也不等于所有可选深化均已完成。

### 4.1 M1：源码分析与性能诊断

必须完成：

- **M1-01**：在锁定源码版本上建立请求进入、调度、KV 分配/释放、模型执行、Attention 和输出的相关调用链，标注实际文件、函数和 commit。
- **M1-02**：对原生指标不足的关键路径实施可开关的运行时插桩；保存真实请求的事件或统计，并评估插桩开销。
- **M1-03**：至少对 Prefix 复用、长短请求排队和 Decode 执行开销做实际分析，区分观测、推测和已经验证的因果结论。
- **M1-04**：形成 baseline 与初步诊断报告，说明下一步优化依据或未发现预设问题的原因。

不能仅提交阅读笔记、源码截图或通用 Transformer 知识作为完成证据。

### 4.2 M2：Prefix-aware 冷热缓存与长度感知调度

必须完成：

- **M2-01**：实现明确的冷热区分、有效复用统计与缓存保留/淘汰规则，并接入真实引擎 KV 生命周期。策略可简单，但需要说明状态转移和维护开销。
- **M2-02**：维护引用计数、共享块、hash 与 block table 等实际不变量；不得淘汰仍被请求使用的块。覆盖实际支持路径中的分配、释放、取消和 block 重用。
- **M2-03**：长度感知规则真实影响请求选择或 admission，使用推理时已知信息，并有防止长请求系统性饥饿的基本机制。
- **M2-04**：完成原生基线、仅 cache、仅 scheduler、两者组合的对照，记录命中口径、等待/延迟、吞吐、失败和长短请求分组结果。

缓存策略模拟器或服务外部按长度排序，可以用于准备和分析；它们不能单独代替本主线要求的引擎集成。

冷热分层初版默认指同一 GPU KV 池内的保留与淘汰优先级，不自动意味着 CPU/GPU 分层存储。Prefix 复用直接减少重复 Prefill，不等于减少每个 Decode token 的历史 KV 读取。

### 4.3 M3：自适应推测解码与 Draft 蒸馏

必须完成：

- **M3-01**：验证目标模型与 Draft 的模型、词表、token ID、特殊 token、模板及所选 vLLM 方法兼容，并跑通固定 K 对照。
- **M3-02**：实现基于近期滑动窗口接受情况的 K 调整；调整实际发生在运行过程中，并影响提议和验证使用的候选长度，而不是重启服务切换配置。
- **M3-03**：保留正确的验证、拒绝/回滚和结束处理；记录控制器决策轨迹，具备稳定性或回退措施。上游已覆盖的机制可以复用，但须明确个人增量。
- **M3-04**：实际使用冻结教师生成或提供的训练信号训练 Draft，保存数据来源、训练 recipe、训练日志和模型产物；基础版允许小规模序列级蒸馏。
- **M3-05**：将训练后的 Draft 加载到真实评测路径；在固定 K 下比较蒸馏前后，再在固定 Draft 下比较固定 K 与自适应 K，分离贡献。

只接入现成 Draft、生成教师数据但未训练、只做离线 K 模拟，均不能满足整条主线。负收益不能免除训练和真实控制实现要求；但可以成为默认关闭该功能的依据。

### 4.4 M4：AWQ W4A16 与层敏感性分析

必须完成：

- **M4-01**：从明确来源模型完成可复现的 AWQ 校准与导出，并验证量化模型能被实际 vLLM 配置加载和推理。
- **M4-02**：比较通用与车载任务校准数据；控制数据预算并记录实际 token 数、来源与 split。
- **M4-03**：对有说明理由的代表性层或层组做量化敏感性实验，保存对任务指标/误差的影响，并用结果支持配置选择；不要求基础版全层搜索。
- **M4-04**：比较至少两种后端实际支持的 Group Size，并记录显存、吞吐/延迟与任务指标；若无法提供第二种受支持配置，须记录缺口并解决或请求范围调整。
- **M4-05**：区分权重占用、固定 KV 预算下的运行显存，以及固定总显存预算下的 KV 容量。若部分层保留高精度，明确混合精度范围。

仅下载现成 AWQ 权重不算完成校准流程；只换校准集不算层敏感性分析。无需为了原稿之外的“Task-aware”措辞强行修改量化目标。

### 4.5 M5：RoPE 与 KV Cache Append 融合 CUDA Kernel

必须完成：

- **M5-01**：查明目标 vLLM 路径的数据语义、布局和上游已有融合能力，说明自定义实现的来源与个人贡献。
- **M5-02**：编写真实融合 CUDA 实现，使一次融合计算完成所声明的 RoPE 与 KV 写入工作；明确支持的 dtype、shape、stride、GQA、RoPE 形式和 cache layout。
- **M5-03**：对 Q 和缓存中的 K/V 分别做数值一致性检查，覆盖声明支持范围内的边界和未写 slot，执行适当的内存错误检查。
- **M5-04**：以等价的独立执行路径作为微基准，使用 CUDA Event、预热、多次重复和正确同步，排除不属于目标比较的编译/分配等开销。
- **M5-05**：保存源码、测试、编译环境、shape 清单和原始计时；若上游融合支持相同设备和形状，纳入比较或说明未能公平比较的具体原因。

基础版允许独立算子原型，不强制接入端到端 vLLM；不得因此声称服务 TPOT 改善。调用上游已有融合 kernel 而没有自己的融合实现，不能满足 M5-02。

### 4.6 M6：FA2、Nsight 与单/双卡部署

必须完成：

- **M6-01**：实际启用和评测 FlashAttention-2 的 Prefill 路径，保存 backend 选择和 kernel 证据；明确可用的比较对象与版本限制。
- **M6-02**：采集并解释 Nsight Systems 的真实执行时间线，分析 Prefill/Decode、CPU gap、Kernel Launch 和适用情况下的通信开销。
- **M6-03**：实际完成单卡、双副本、TP2 三种部署的小规模请求运行与性能记录，保存机器拓扑和实际通信路径。
- **M6-04**：至少覆盖不同长度和并发条件，形成与证据一致的初步配置建议；双副本与 TP2 按相同两卡预算比较，单卡另作资源效率参考。

只写部署配置但不启动、只安装 FA2 但未使用、只给通用 Nsight 图解，均不能满足对应要求。

### 4.7 覆盖矩阵与证据要求

agent 必须维护以上 **27 个要求 ID** 的覆盖矩阵。每行至少包含：

```text
requirement_id | stage | status | code_sha/path | test_evidence
run_ids | artifact_refs | explanation_path | limitation
```

状态至少区分 `planned`、`in_progress`、`implemented`、`validated`、`blocked`。空证据、占位路径和“应该能运行”不能标记为 `validated`。阶段 2 完成时，27 项全部达到其最低验收要求；阶段 3–6 的发布继续满足这些要求并更新相关证据。

## 5. 六大阶段的完成与验收目标

### 5.1 阶段总览

| 阶段 | 定位 | 完成后的版本状态 | 建议阶段 tag |
|---|---|---|---|
| S1 | 空仓库与基础环境搭建 | 内部准备版，不宣称六条工作完成 | stage-1-foundation |
| S2 | 六条主线的最小完整实现 | 基础可面试版 | stage-2-complete-basics |
| S3 | 六条主线的工程与实验完善 | 稳定可面试版 | stage-3-validated |
| S4 | 基于实测瓶颈的重点深化 | 深入版 | stage-4-depth |
| S5 | 组合优化与完整场景验收 | 最终候选版 | stage-5-release-candidate |
| S6 | 最终发布与面试材料固化 | 最终完成版 | v1.0.0 |

tag 名可以按仓库约定调整，但必须唯一指向已完成对应验收的版本。不得预先创建表示完成的 tag。

### 5.2 每个阶段共同要求

每阶段必须记录：目标、进入条件、六条主线状态、交付物、验收证据、关键提交、阶段结束报告。阶段报告还需列出未解决问题、默认启用功能、实验功能、资源使用与下一步。

阶段可以穿插实施准备；正式完成状态须按前序验收递进。开始研究 S4 的某个方向，不意味着 S2、S3 可以跳过。

#### S1：空仓库与基础环境搭建

**目标与进入条件**：从空仓库或用户提供的现有初始化目录建立可开发、可测量的基础；先检查已有内容，不覆盖已有用户工作。具备可用 GPU 前可完成 CPU 部分，但阶段最终验收包含实机链路。

**六条主线目标状态**：全部完成范围与兼容性预检，建立待实现清单，不要求实现六条最小闭环。

**必须交付**：

- 独立 DriveServe Git 仓库、项目说明、可安装入口、基础检查和 GPU smoke 入口。
- 锁定的 vLLM 源码基线与可复现修改方式，环境/模型/后端兼容矩阵。
- 按第 2.5 节交付环境恢复/重建入口、经核实的持久存储范围及资源配置说明；实际迁移未发生时明确标注。
- 可用任务 schema、数据来源与划分规则、prompt、评分器、小样本和真实 vLLM 推理 Demo。
- 按第 6.1.1 节明确性能、质量、校准和蒸馏的数据用途、获取/构建方案及测试冻结规则；后续所需完整数据随对应主线实施。
- baseline 测量入口，能记录请求、错误、时间、token 数、环境与配置；指标定义已固定。
- 初始覆盖矩阵、进度文件、资源计划、关键技术风险与 GPU 截止日期。
- 按第 9.7 节建立阶段内保存与恢复约定，记录保存触发条件、周期、任务状态和恢复入口。
- 从零到 S1 的讲解材料，明确当前哪些工作尚未做。

**验收条件**：

1. 从当前文档能安装和启动真实服务，完成场景输入→输出→评分→记录链路。
2. 主要模型、Draft 方法、量化格式、FA2、编译模式和 TP2 的可用性经过小规模实机检查；失败项有明确记录和处理决定。
3. baseline 入口至少真实运行一次，指标可从原始数据计算；mock 数据完全分离。
4. 仓库、环境和资产索引可追踪；阶段状态不包含未经验证的性能数字。
5. 已验证环境按保存定义恢复或重建，并完成相应基础检查；持久资产可读回。实际迁移的核验在发生时补做，不以未发生迁移阻塞 S1。
6. 通过一次小任务的中断恢复演练：仅靠落盘记录、Git 和实际任务状态即可找到进展、保留原始记录并继续，且不会重复启动仍在运行的任务。可在当前实例内演练，不要求真实关机或换卡；训练续训在引入训练后验证。

**Git 与结束报告**：保留初始化、任务/数据、评测、环境冻结等关键提交；验收后创建 S1 tag，报告实际环境和下一阶段最短闭环计划。

#### S2：六条主线的最小完整实现

**目标与进入条件**：S1 已验收，取得真实执行所需的环境；六条主线全部完成第 4 节最低要求，形成第一个可面试完整版本。

**六条主线目标状态**：

| 主线 | S2 必须达到的状态 |
|---|---|
| M1 | 有真实插桩、源码调用链、baseline 和初步诊断 |
| M2 | 简单冷热策略与长度感知调度实际接入，四组对照可运行 |
| M3 | 固定 K、自适应 K、实际小规模蒸馏及分离贡献的比较均完成 |
| M4 | AWQ 校准/部署、两类校准数据、有限层敏感性和多 Group Size 比较完成 |
| M5 | 自定义融合 CUDA 原型、数值/内存检查和等价微基准完成 |
| M6 | 真实 FA2、Nsight 和三种部署的代表性实验完成 |

**必须交付**：六条实现/实验代码、可开关配置、必要正确性测试、原始运行及产物索引、覆盖矩阵、初版结果表和累计讲解包。

**验收条件**：

1. M1-01 至 M6-04 的 27 项要求逐项提供证据，不能以阅读、规划、mock、未运行代码替代。
2. 每条至少有可重放命令或脚本入口，以及实际运行成功的记录；优化类实验有匹配对照。
3. 基础正确性、任务有效性和关键失败处理通过；受支持范围明确，不需要泛化到所有模型和输入。
4. 自适应、蒸馏、cache、scheduler、量化等贡献分别可识别，不以混合改动解释全部收益。
5. 小样本结果标记为探索性。尚不稳定的 P99 可以如实记录并留待 S3 补强，不能写成确定的最终收益。
6. 累计材料能够解释六条实际做法，事实版简历不含未验证百分比和未做过的动词。
7. 实际蒸馏训练按第 9.7 节验证 checkpoint 恢复；新增长任务纳入阶段内保存与恢复约定。

**Git 与结束报告**：每条主线保留独立实现/验证提交，报告原生能力与个人修改；验收后创建 S2 tag。已实现但无收益的功能保留可运行 profile，默认状态按证据决定。

#### S3：六条主线的工程与实验完善

**目标与进入条件**：S2 已验收；将可运行的基础实现完善为结果可信、边界清楚的稳定版本。

**六条主线目标状态**：

| 主线 | S3 的完善重点 |
|---|---|
| M1 | 插桩开销、计时口径、异常请求与负载发生器可靠性，诊断与证据一致 |
| M2 | 引用计数/共享/取消/抢占/重用等适用边界，公平性与策略维护开销 |
| M3 | K 切换、EOS、拒绝回滚、动态 batch、编译模式及蒸馏数据隔离 |
| M4 | 校准可复现性、质量阈值、敏感性口径、显存分解及后端一致性 |
| M5 | 支持范围边界、数值容差、内存安全、重复计时及上游融合对照 |
| M6 | 后端选择真实性、相同资源预算、路由策略、拓扑与正式计时的公平性 |

**必须交付**：正确性/回归检查、扩展后的实验配置、重复运行、异常与负结果、稳定性报告、更新后的累计讲解和简历证据映射。

**验收条件**：

1. 已声明支持范围的关键边界通过检查；未覆盖范围显式限制，不以扩大措辞掩盖空白。
2. 核心结果具备独立重复，报告样本量、波动、失败率与条件；测试集不参与调参。
3. baseline 包括合理调优的原生 vLLM；不是关闭已有优化制造差距。
4. 从结果摘要能回溯原始数据，从原始数据能重新聚合核心指标。
5. 已发布基础能力保持可运行；修复涉及核心路径时重跑受影响验证。
6. 面试材料新增错误定位、被否决方案、为什么实验可信及不能推出什么结论。

**Git 与结束报告**：正确性修复与性能优化分清，必要时保留问题复现提交；报告相对 S2 的变化、回归结果和仍存在的不确定性，验收后创建 S3 tag。

#### S4：基于实测瓶颈的重点深化

**目标与进入条件**：S3 已验收；根据实测价值和剩余资源，形成至少两个可以深入追问的技术点，同时保持六条完整覆盖。

**深化选择**：agent 应记录候选方向、瓶颈证据、预计收益来源、验证成本和选择理由。至少一个深化点涉及真实推理引擎或 CUDA 执行路径的实质性修改；另一点可以来自不同主线，或来自同一主线中独立、可分别验证的问题。

可选方向包括更完善的冷热策略与衰减、调度公平性、接受率与成本结合的 K 控制、Draft 训练方法、量化敏感性驱动配置、CUDA shape 优化/端到端接入、部署路由策略等。它们不是要求全部实现的新增清单。

**六条主线目标状态**：选中方向做深，其余方向维持 S3 的实现与验收水平并做必要回归。不得删除未重点深化的主线。

**必须交付**：至少两个深化专题，每个包含问题、既有方案、修改、正确性、消融、成本、边界与结论；对应实现和实验保留版本。

**验收条件**：

1. 深化不是仅多跑几组参数或把上游开关重命名；每个专题有实际技术工作和可解释的对照。
2. 至少一个专题包含引擎或 CUDA 路径的实质性代码修改与真实运行验证。
3. 实验支持结论；如无收益，完成充分验证、原因分析和合理回退，也可以通过专题验收。
4. “更深”不要求论文级创新或所有方向生产级泛化；工作量与四个月学生项目定位相符。
5. 六条主线累计讲解更新，能解释基础版为何那样实现、深入版改了什么、付出了什么成本。

**Git 与结束报告**：保留关键迭代与失败方案，给深化专题关联实验 ID；验收后创建 S4 tag。不能因租期接近结束就自动把未完成专题判为完成。

#### S5：组合优化与完整场景验收

**目标与进入条件**：S4 已验收；验证实际可组合功能的正确性、交互和场景适用性，完成 GPU 侧最终复测与资产归档。

**六条主线目标状态**：M1 支持整体诊断；M2/M3/M4 验证关键交互；M5 若已接入则参加端到端验证，若仍为独立 kernel 则单独归档且不计服务收益；M6 输出最终部署建议。

**必须交付**：兼容矩阵、有限且有理由的组合/消融、最终 profile、质量与性能回归、单卡/双副本/TP2 比较、GPU 资产清单和累计讲解。

**验收条件**：

1. 区分单项收益和组合收益，不相加或机械相乘各项百分比。
2. 至少验证 cache×scheduler，以及计划启用的量化×spec 等关键交互。无法组合的功能保留独立 profile 与具体限制。
3. 不要求所有功能强制同时开启；最终配置由负载、质量、资源与实测表现决定。
4. 关键场景报告延迟分布、吞吐/goodput、失败与质量，三种部署在公平口径下比较。
5. 核心结论对应冻结代码与环境；GPU 到期前完成受影响路径的最后复测、关键原始记录和模型产物备份及校验。
6. 累计讲解能解释为什么选定这些组合，以及什么情况下应关闭某项优化。

**Git 与结束报告**：以实际验证配置生成 release candidate，引用所有最终 run ID；验收后创建 S5 tag。当前默认关闭的已实现功能，仍须能通过独立入口回放。

#### S6：最终发布与面试材料固化

**目标与进入条件**：S5 已验收；发布可复现、可审计、可讲解的最终完成版。

**六条主线目标状态**：全部保留已验证实现和证据；本阶段无需为了发布再增加新功能。新增核心改动必须回到相应验收流程。

**必须交付**：项目 README、快速开始、复现说明、最终报告、结果索引、数据/模型/环境清单、各阶段可获取版本、最终六条事实版简历和完整学习/讲解包。

**验收条件**：

1. 在干净 checkout 中验证文档、脚本、路径和资产获取；完整 GPU 复现若已在 S5 的冻结实现上完成，明确引用该证据，不在无 GPU 时声称再次执行。
2. 所有关键实现 commit、vLLM 改动和阶段 tag 可获取；核心资产不能仅保存在即将释放的机器上。
3. 报告数字由版本化脚本和真实原始数据产生；原稿占位数已从事实版成果中移除。
4. 27 项基础要求和阶段深化/组合目标有完整证据索引，允许明确记录负收益和不支持范围。
5. 用户可通过材料理解从 S1 到 S6 的全部工作，能定位关键实现、实验与决策。
6. 项目所有者“是否已经独立掌握”另行记录；agent 不因生成讲解稿就宣称用户已经通过面试或理解全部内容。

**Git 与结束报告**：验收后创建最终发布 tag，记录与 S5 的代码差异和所需回归范围；发布报告说明真实完成程度、适用边界与后续可选工作。

## 6. 实验与指标规范

### 6.1 基线、数据与工作负载

1. **保留两类原生基线**：锁定版本的原生配置 B0，以及在合理开发预算内调优后的原生 vLLM B1。主要自研收益与 B1 比较，必要时同时展示 B0。
2. **先核查上游能力**：APC、chunked prefill、动态 K、量化和融合路径可能随版本改变。保存实际配置、后端日志和来源，不以关闭已有能力后的差距作为唯一创新证据。
3. **固定数据口径**：记录任务、标签、prompt/template、tokenizer、长度与前缀分布。训练、校准、开发和最终测试按场景/轨迹/来源隔离，防止相邻帧或重复模板造成泄漏。
4. **独立任务评估**：teacher 输出可用于蒸馏，不应成为证明车载任务正确性的唯一真值。规则、人工或数据集标签的局限必须说明。
5. **代表性负载**：至少包含短输入短输出、长输入短输出、长短混合、热点前缀、热点与一次性请求混合，以及用于投机分析的较长输出。agent 决定实际长度与比例并保存配置。
6. **业务与压力测试分开**：为测机制构造的长输出、重复前缀、填充 token 等标注为合成负载，不能直接推广为真实车载业务收益。
7. **先确认模型任务有效性**：若目标模型输出几乎不可用，应先修正任务/提示或作必要适配，再冻结目标模型。模型变化后不能沿用旧性能对照而不说明。
8. **预算约束**：不盲目穷举参数组合。先探索、定位，再选定主比较做充分验证；保留选择依据。

#### 6.1.1 数据获取与构建最低要求

**必须达到的效果**：数据足以支撑六条主线的公平性能对照和独立质量评估，不要求大规模真实自动驾驶多模态数据集。可先用小规模结构化代理任务跑通，再按实际实验需要扩充；统一请求压测环境不能替代质量、校准与蒸馏数据要求。

| 用途 | 最低要求 |
|---|---|
| 性能请求与压力负载 | 固定或可重建输入、长度/前缀分布、到达轨迹、生成参数和 seed；匹配对照使用相同负载，明确真实任务与合成压力请求 |
| 任务质量评估 | 有明确标签或规则、评分器和独立冻结测试集；检查基线、量化和蒸馏相关结果，不能仅以吞吐或 Draft 接受率证明任务质量 |
| AWQ 校准 | 有可追溯的通用及车载校准数据，能说明选择和采样方式；与最终测试隔离，支持校准类型和 Group Size 等对照 |
| Draft 蒸馏 | 有明确训练/开发划分，记录教师生成或其他监督来源、生成配置和过滤过程；最终评测使用未参与训练和调参的数据 |

公开数据、自建数据或混合方案由 agent 根据任务和预算选择，记录选择理由、来源及许可/使用限制。自建或生成数据需保存生成规则/脚本、配置、seed 和必要原始产物；不保证可重新获取或生成完全一致的数据应保留固定副本。算子正确性与微基准可以使用有代表性的张量样例，无需强行使用业务数据。

数据数量和具体名称不预先写死，但必须足以支撑所报告结论；小样本与合成数据的适用边界应明确。四类用途可以来自同一数据源的不同划分，不要求维护四套独立平台；按场景、轨迹或来源隔离训练/校准/开发与最终测试，记录版本、划分、样本数和 hash。正式对照冻结数据与评分规则；变更时创建新版本并复测受影响对照，不悄悄替换样本或据最终测试挑参数。

### 6.2 指标定义

| 指标 | 必须记录的口径 |
|---|---|
| E2E latency | 实际发送到请求结束的时间；另记录计划到达与实际发送，必要时报告包含客户端排队的用户侧延迟 |
| TTFT | 实际发送到首个有效输出 token/内容的时间；说明计时位置和网络范围 |
| TPOT | N>1 时，请求级平均可用 `(最后 token 时间−首 token 时间)/(N−1)`；说明 token 计数来源，不把它直接称为某个 Decode kernel 的时间 |
| ITL | 真正逐 token 的间隔需可靠 token 时间戳；流式 chunk 可包含多个 token，投机输出尤其如此 |
| P99 | 标明是 E2E、TTFT 还是请求级平均 TPOT 的 P99，以及样本数、失败/超时处理 |
| Throughput | request/s 和实际输出 token/s 分别记录，注明测量窗口与完成/失败口径 |
| SLO goodput | 满足预先定义延迟/成功条件的完成请求/s；加入任务质量时明确规则 |
| Prefix hit | 至少说明请求/块/token 哪一种分子分母；推荐同时报告实际复用 prompt token 和减少的 Prefill 工作量 |
| Draft acceptance | 实际被接受的 Draft token / 实际提议 Draft token，不含 target bonus token |
| Acceptance length | 每次验证接受/输出长度分布，明确是否包含 bonus；EOS、约束截断和剩余长度单列 |
| Memory | 权重驻留、KV 分配/使用、workspace/graph、峰值与总占用按可观测范围分解 |
| Quality | JSON 有效率、关键行为/字段指标、规则通过率等，与实际任务标签相符 |
| GPU 利用情况 | 若声称改善 GPU 利用率，给出对应利用率/有效吞吐指标与采样方法；不能只凭显存下降推断 |

比例写法统一：延迟下降为 `(baseline−new)/baseline`，吞吐提升为 `(new−baseline)/baseline`。命中率从 40% 到 55% 是增加 15 个百分点，不能无说明写成相对提升 15%。

量化比较至少区分固定 KV 预算和固定 GPU 总预算。相同 `gpu_memory_utilization` 不保证 KV 容量相同，nvidia-smi 总占用也不直接代表模型权重大小。

### 6.3 正确性与等价性

- cache 和 scheduler：检查生命周期与预算不变量，覆盖真实支持的取消、共享、抢占/恢复路径；解释调度变化可能影响随机数消费或数值行为。
- speculative decoding：保持相应 target 的验证/拒绝采样语义；greedy 做适当输出一致性检查，随机采样用匹配其逻辑的分布/统计测试，不强求不同执行路径随机序列逐 token 一样。
- 量化：质量本身允许按预定义阈值变化，因此报告质量—资源—速度的取舍；阈值在最终测试前确定。
- kernel：比较等价工作和真实写入结果，明确 dtype 容差、边界、布局与内存安全。必要时检查未写区域不变。
- 量化 target 的投机解码应与同一量化 target 的普通解码比较采样正确性；不能宣称它自动保持原 BF16 target 的分布。
- 具体测试由 agent 依据风险设计，避免为低风险文档改动重复 GPU 测试，也避免以大量只镜像实现的单元测试替代集成检查。

### 6.4 性能测量要求

1. 固定并发闭环用于容量曲线，独立到达率开环用于排队与尾延迟；明确各自用途。
2. 开环保存计划到达与实际发送，不让上一请求完成时间决定下一请求到达；记录客户端发送滞后，排除负载发生器瓶颈。
3. 超时、失败、拒绝、取消不能从成绩中消失。完成请求 P99 必须伴随完成率、超时设置和失败率。
4. 热身、编译、图捕获与正式测量分离；Prefix Cache 冷/热状态独立控制。A/B 使用相同轨迹和 cache 状态口径。
5. 固定或记录硬件、功耗/温度状态、模型、采样、长度、KV 预算、并发/到达率与后端。训练或另一卡负载可能影响共享 CPU、PCIe 和散热，正式比较应避免混杂。
6. profiling 与正式性能测量分开；不能将 Nsight 开启时的运行当作无采样最终成绩。插桩本身也要评估成本。
7. S2 允许小规模探索；S3 起关键比较原则上至少做三次独立重复。P99 的主结论应尽量基于每次约一万请求或其他有充分理由的统计预算；不足时报告不确定性，不伪称稳定收益。
8. 交替或随机化 A/B 次序，报告重复间差异。使用置信区间时记录计算方法与重采样单位，考虑请求的时间相关性。
9. 正式测试前冻结关键配置和结论判定标准；调参用开发负载，最终测试不用来反复挑最佳参数。
10. “没有显著收益”“只在某种合成负载收益”“以质量或长请求延迟为代价”都应记录；不得只保留最好一次。

### 6.5 组合与归因

- cache 与 scheduler 至少有独立和联合对照；蒸馏与动态 K 至少有固定另一个因素的对照。
- 融合算子比较的是等价独立路径总耗时；已有上游融合可比较时也纳入，明确复现收益与个人增量。
- 微基准收益不能直接变成端到端收益。用被优化部分占比检查端到端解释是否合理。
- FA2 后端名与实际执行路径一致；Nsight Systems 时间线不足以独立证明 DRAM 带宽饱和，深层硬件瓶颈可由其他计数器补充。
- 双副本与 TP2 对比保持总请求流、质量目标和两卡预算一致；记录副本路由及前缀亲和造成的负载分布变化。
- 4090 的真实拓扑和通信能力必须检测，不能把无 NVLink 的卡当作高速互联服务器推定 TP 收益。

## 7. Git、实验资产与留迹规范

### 7.1 仓库与版本

1. 主项目使用 Git。若尚未初始化则创建；若目录已有仓库或用户文件，先检查，禁止重置、清空或擅自改写已有历史。
2. 涉及 vLLM 核心修改，推荐独立 fork + 主仓库 submodule；也可使用能精确重建的固定上游 SHA + 版本化补丁。不得只修改 site-packages 而没有可恢复源码。
3. agent 自主设置适合个人项目的分支策略，main 应保留可理解的稳定状态。每条关键功能或优化应具有独立、可定位的提交。
4. 本规范要求本地提交与阶段 tag；GitHub owner、remote、可见性和凭据未提供时，不阻塞本地可完成的工作。用户确认的 remote 可按授权同步，公开发布、仓库可见性变化不由文档自动授权。
5. Git 作者身份不可虚构；缺少必要配置时报告所缺信息。提交失败不能记为已提交。
6. 阶段 tag 指向已验收的提交；已对外引用的 tag 不随意移动。修复使用新 commit/tag，保留旧阶段可获取性。

### 7.2 提交粒度

有意义的工作单元应完成提交，例如：

```text
chore: initialize project and execution contract
feat: add structured task and inference demo
bench: establish reproducible upstream baseline
feat: integrate prefix-aware cache policy
feat: add length-aware scheduling with aging
feat: add runtime adaptive draft-length control
train: add sequence-distillation recipe and model manifest
feat: add AWQ calibration and sensitivity evaluation
perf: implement fused RoPE and KV-write CUDA kernel
bench: compare FA2 and single/replica/TP deployments
docs: record stage acceptance and cumulative walkthrough
```

以上是示例，不要求逐条照抄。不能只在项目结束时一次性提交全部实现，也不要求为每个微小编辑建立无意义 commit。

对关键优化应能找到问题/设计、实现、正确性验证、实验/结论四类证据；它们可根据实际范围组织为几个连贯提交。失败路线和回退原因保留在历史或实验记录中。

### 7.3 代码与实验的关联顺序

```text
提交可执行代码与实验配置
  → 确认主仓库及上游修改状态
  → 正式运行并记录实际 code SHA
  → 保存原始数据与资产校验值
  → 聚合结果并提交报告
  → 完成阶段验收后打 tag
```

正式报告引用运行时的代码 SHA，而不是事后报告 commit 的 SHA。实验结果 commit 可以晚于代码 commit，不需要制造“提交必须包含自己的 SHA”的循环。

正式实验原则上使用干净工作树。临时探索若有未提交改动，必须标记 dirty 并保存差异；这样的结果不能直接升级为正式成绩，应在固定代码后复测。

### 7.4 每次实验的最小记录

每次实验有唯一 run ID，重试生成新 ID 并关联先前运行，不覆盖旧原始记录。至少记录：

| 类别 | 字段要求 |
|---|---|
| 身份 | run_id、stage、requirement_ids、hypothesis、baseline_run_id、开始/结束时间及时区、状态 |
| 代码 | DriveServe SHA、vLLM SHA/补丁标识、dirty 标志、聚合脚本版本 |
| 环境 | 环境标识、实际 GPU 型号/数量/每卡显存、拓扑、driver、CUDA、PyTorch、vLLM、构建/镜像标识及必要依赖；迁移或环境变化另行关联记录 |
| 模型 | target/Draft revision、训练/量化产物 hash、tokenizer/template 版本 |
| 数据 | 来源 manifest、split、数据/请求轨迹 hash、实际长度和采样规则 |
| 配置 | 完整展开配置、feature flags、后端、seed、图模式、KV/显存预算、冷/热状态 |
| 负载 | 到达模式、实际 req/s 或并发、请求数、热身、测量窗口和超时 |
| 结果 | 成功/失败/超时数、核心指标、质量、重复编号和局限 |
| 资产 | 原始请求/服务日志、训练日志、profile、模型、summary 的持久位置、大小和 hash |

字段不适用时写明原因；未知信息标记 unknown，不填写看似真实的占位值。

### 7.5 什么进入 Git

| 进入 Git | 存入独立 artifact 存储，Git 保存索引 |
|---|---|
| 源码、测试、配置、依赖锁、任务与数据 schema | 模型权重、完整训练 checkpoint |
| 小型可分享样本、数据来源/划分清单 | 大型数据集、完整请求日志 |
| run manifest、结果摘要、分析脚本、关键图表 | 大型 Nsight trace、逐层大张量 |
| 决策、验收、累计讲解、事实版简历 | 其他超过仓库合理体积的原始产物 |

保存策略应兼顾可复现与空间：最终模型、最终原始数据、关键失败/回归证据不能仅留下摘要；冗余临时 checkpoint 可以按明确记录的保留策略处理。已有用户资产不得因实验清理被擅自删除。

### 7.6 持久化与可获取性

- 每个阶段完成时检查对应证据是否可重新读取；不能只写“已备份”。
- 释放租机前保存环境、源码、模型、原始运行、关键 trace 和 Demo，核验 hash 与读回结果。
- 索引优先使用项目内相对路径或明确的 artifact URI，避免仅依赖某台机器的临时绝对路径。
- 若资产受许可或访问权限限制，记录获取方式和限制；不要在公开复现说明中宣称任何人都能访问。
- 阶段 2 以后至少保存各阶段关键发布配置所需的模型/参数与证据，不能只留最终版而丢失基础版。

## 8. 阶段讲解、学习与面试材料要求

### 8.1 每阶段累计讲解包

S1–S6 每阶段都要生成累计材料。S1 可以明确哪些工作未完成；S2 起六条主线均应有实际代码和实验可讲。

建议使用 `docs/stages/Sx/`，文件可合并，但以下内容不能缺失：

| 材料 | 必须回答的问题 |
|---|---|
| 阶段验收报告 | 本阶段是否完成，每项条件的证据在哪里，哪些问题未解决 |
| 项目全景与演进 | 项目解决什么问题，从空仓库到当前版发生了哪些关键变化 |
| 六条主线实现讲解 | 每条具体做法、输入输出、控制流、关键源码、个人修改与上游边界 |
| 源码阅读路线 | 从哪个入口开始，按什么顺序阅读函数/模块，如何关联一次真实请求 |
| 决策与失败案例 | 为什么选当前方案，尝试过什么，怎样定位失败，为什么回退 |
| 实验解释与复现 | baseline、配置、绝对指标、比例计算、样本量、负结果、复现入口 |
| 分层讲解稿 | 简短项目介绍、完整技术讲解、可追问的深入专题 |
| 事实版简历与映射 | 当前可以使用的六条表述，各自对应 commit、run ID、报告和条件 |
| 已知限制与学习清单 | 当前不支持或未证明什么，项目所有者还有哪些知识点待理解 |

讲解要使用当前实现的变量、数据结构、调用顺序、配置与真实样例；不能用泛泛的术语解释代替工程事实。

### 8.2 每条主线的固定讲解问题

1. 为什么项目需要这一部分？观察到了什么问题或研究机会？
2. 原生 vLLM 或原生算法如何处理？已有能力是什么？
3. 我具体修改/训练/实现了什么？代码入口与关键数据结构在哪里？
4. 一次请求或一次算子调用如何经过这些逻辑？
5. 最小版本为什么采用这个方案？深入版本如何变化？
6. 怎么检查正确性？有哪些容易犯错的边界？
7. 对照实验如何设计，数字怎样计算，有没有其他解释？
8. 在什么条件下无收益或退化？多付出了什么时间、显存或复杂度？
9. 没做什么，后续如果继续做会优先解决什么？

### 8.3 面试追问材料

每条主线至少准备三类有实际依据的追问：原理与实现、实验与正确性、限制与权衡。答案必须链接到当前阶段实际证据；没有完成的探索应直接说明。

可以提供约 2 分钟介绍、约 10 分钟项目讲解，以及按专题展开的深入版本。时长是组织参考，不要求机械凑字数。

阶段材料必须支持“只查看 S3 资料即可讲清从 S1 到 S3”，不要求用户自行拼接十几份增量日志。旧阶段资料同时保留，方便面试时解释演进。

### 8.4 用户掌握状态与工程状态分离

agent 负责交付可理解的材料和演练问题，可按用户要求进行实际追问、复述检查和反馈。学习记录至少区分未讲解、已讲解、用户已复述、追问已验证。

没有用户实际参与时，不得声称用户已经掌握。工程阶段通过不依赖用户必须先完成学习；如果用户收到面试，可立即基于最近一个已验收完整版本生成针对性讲解，仍以该版本事实为准。

## 9. Agent 自主执行、状态管理与异常处理

### 9.1 首次启动与每次恢复

agent 首次接管或恢复任务时，应：

1. 阅读本规范、项目 `AGENTS.md`、`docs/progress.md`、覆盖矩阵与最近阶段报告。
2. 检查 Git 分支、工作树、最近提交、tag、上游引用与已有用户改动。
3. 检测实际环境、GPU 租期/可用性和资产存储；区分已有事实与旧记录。
4. 对最近进度与真实文件/运行记录做必要核对，不能只相信自然语言“已完成”。
5. 维护当前阶段的具体执行计划和下一步，优先处理依赖与资源期限。
6. 继续已授权范围内的工作；不要因为上下文中断就重建仓库、重训模型或重复全部实验。

该流程不要求固定使用某种任务管理工具，也不要求自动创建其他聊天或子 agent。

### 9.2 agent 可自主决定的事项

- 具体实现算法、内部模块组织、合理依赖版本和开发工具，前提是维持用户确认的主线与兼容要求。
- 阶段内任务顺序、代表性实验矩阵、有限调参预算、测试方式和合理的代码重构。
- 根据正确性、性能和证据选择默认配置，保留实验功能、负结果和回退路径。
- 在阶段门槛满足后继续下一阶段，同时留下报告；不要求每阶段都再次请求“是否继续”。

### 9.3 需要用户决定的事项

只对必要问题提出具体选项，并继续不依赖该答案的工作，例如：

- 新增付费算力、延长租期或超过已授权预算。
- 无法在现有约束下兑现六条基础要求，需要缩减主线或改变明确指定的模型/功能目标。
- 缺少 Git 作者信息、GitHub remote、模型访问或存储权限等无法自行推定的信息。
- 发布可见性、删除已有用户资产、改变现有共享资源等超出已授权范围的动作。

问题应说明具体阻塞、已尝试方法、建议选择、成本和影响；文档不要求在无真实风险或无缺失信息时反复询问。

### 9.4 进度文件

`docs/progress.md` 至少维护：

```text
当前阶段 / 当前可面试发布版本
本轮完成的具体工作与证据
六条主线和各要求状态
最近代码提交、实验与资产位置
当前未提交改动或运行中的任务
阻塞、已尝试方案与待用户决定事项
GPU 租期、剩余资源与备份状态
下一步可执行动作与预期验收
```

阶段状态建议使用 `not_started`、`in_progress`、`verification_pending`、`accepted`、`blocked`。这里的 blocked 是项目状态，不授权改变平台其他任务/目标工具的状态规则。

“implemented”表示代码已实现；“validated”要求对应测试/运行证据；阶段“accepted”要求本阶段完整交付，不能通过将未完成项标注为“可选”绕过原规范。

### 9.5 技术决策与偏差记录

影响后续解释或复现的选择应写 ADR/决策记录，至少包含：问题、可选方案、证据、决定、影响、相关提交与复查条件。例如 vLLM 版本、为何选择某种 cache 策略、为何关闭 spec、为何量化保留部分层等。

若发现规范某项在现有环境下不兼容或不现实，提交具体偏差说明，保留原要求为未满足。未经用户确认，不把“无法运行”改写成“已完成分析，等价通过”。

### 9.6 失败、负结果与回退

- 实验失败保留 run ID、失败阶段、日志、原因分类和后续动作。
- 性能无收益时先核查测量与实现，再决定保留、修正或默认关闭；不得调整统计口径掩盖结果。
- 正确性失败优先回退到已验证路径，保存复现与修复证据；对应优化暂不能进入发布默认配置。
- 上游已有更好的实现时，准确报告比较，允许项目产出为学习性复现或特定形状研究，不虚称通用领先。
- 预算不足时优先保护已有完整版本、最终回归和备份，并明确未完成阶段；不能用“总工作量预计四个月”替代实际 GPU 验证。

### 9.7 阶段内保存与恢复最低协议

**必须达到的效果**：任务失败、实例迁移或对话上下文结束后，接管 agent 能从持久记录识别实际完成程度、仍在运行的工作和下一步，无需依靠旧对话全文重做阶段。意外中断可能丢失最近一次有效保存后的工作，应明确保存周期与恢复粒度，不承诺零丢失。

1. **规定保存时机。** 完成有意义的工作单元、实验启动/完成/失败、计划切换对话或迁移前，及时更新进度与相关证据；关键代码按第 7 节提交。长时间运行的任务还须周期保存状态、日志及适用的 checkpoint，不能只等阶段结束或聊天结束。具体周期由 agent 按任务时长、开销与可接受损失选择并记录。
2. **保存足够的交接信息。** 至少包括当前阶段/子任务、最近 commit、未提交改动、最近更新时间、环境、run ID、实际进程或作业标识、启动入口与配置、日志和资产位置、有效 checkpoint、失败及已尝试方案、下一步动作与验收条件。进度摘要可引用独立任务记录，不必把全部日志塞入一个文件。
3. **长任务自身落盘。** 训练和实验的日志及保存机制不能只依赖 agent 对话仍在运行。训练 checkpoint 应能按所用方法恢复训练进度和必要状态，例如优化器、调度器及随机状态；仅能加载权重重新训练的产物不能冒充完整续训。保存须可校验，避免半写文件覆盖唯一有效记录；具体工具与完整性措施由 agent 决定。
4. **核验后继续。** 恢复时按第 9.1 节检查实际文件、环境和任务状态，识别成功、失败、中断与仍在运行的任务，不能只凭旧 PID 或文字状态判断。先确认已有进程/作业是否有效，再决定接管、续跑或新建，避免重复训练和争抢 GPU；失败重试保留旧记录并使用关联的新 run ID。
5. **区分续训与重新测量。** 训练从确认有效且兼容的 checkpoint 恢复并记录来源；不能续训时说明原因。中断的 benchmark 保留为不完整记录，重新运行受影响的完整测量单元；环境变化后按第 2.5 节重建对照，不将不同硬件或中断前后的性能片段拼成一次完整运行。
6. **会话交接以文件为准。** 单个对话无需完成整个阶段，也不要求用户为续接手动开启多个并行对话。新会话读取规范、进度、Git 与任务记录即可接续；未授权时不自动创建新聊天。若已获授权并行工作，另行记录任务归属，避免多个 agent 同时改同一状态或重复实验。
7. **明确运行机制的边界。** 必须交付可恢复能力；是否使用进程守护、任务队列或平台自动恢复由 agent 按平台能力选择。文档不会让 agent 在关机、会话终止或凭据失效后自动醒来；未部署并验证的自动重启能力不得写成已有功能。需要用户或平台重新启动时，在进度中给出最短恢复入口；无 GPU 时先做独立工作并保留待验证项。

S1 用小任务验证记录与恢复链路，后续在引入训练或新的长任务类型时验证对应恢复能力并保存证据。验证可有计划地中断并恢复一个小规模运行，不要求人为制造真实断电或重新购买算力。
