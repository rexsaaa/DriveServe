## 1. 怎样使用这份指南

1. **先建立项目骨架**：知道任务、模型与框架、六条工作的关系，再进入操作，不必先学完全部原理。
2. **亲手走通一个小流程**：按第 5 节完成服务启动→请求→压测→分析→对照，遇到概念缺口时补第 3 节。
3. **结合现象学习六条主线**：每次看一段相关代码和一份结果，解释刚才发生了什么；先覆盖六条，再深入薄弱项。
4. **复算数字、补广度、做模拟**：用第 7 节分别检查能否解释、操作和判断结果；未通过的地方回到对应模块。

**操作由你亲手执行，辅导者解释关键参数、提示观察点并协助排错。** 可以查文档，不要求背命令；应能说明命令做什么、输入输出在哪里、为何改某个参数。辅导者代跑并汇报结果，只能算演示。每次先完成一个小任务，再解释观察到的现象，避免一次铺开全部脚本和术语。

每条主线只需先整理一张讲解卡：**问题 → 原理 → 具体改动 → 对照实验 → 结果 → 限制**。附一个代码入口和一份证据，不必背文件名、行号或所有 run ID。

项目骨架必须讲清：输入是道路、障碍物、车辆状态等结构化信息，输出行为、速度区间和让行字段；规则负责评分；Qwen 负责生成，vLLM 负责推理执行与资源管理。它是车载决策代理任务，不是实车感知—规划—控制闭环。区分上游能力、项目增量和本人实际参与。

## 2. 六条简历：必须准备到什么程度

六条均为必修；“实现、自编、分离贡献”需要核心代码和实验层面的理解。

| 主线 | 至少要理解 | 至少要能完成 |
|---|---|---|
| **源码分析与诊断** | 固定 vLLM 0.8.5 V0 的请求进入、排队、调度、KV 分配、模型执行、输出与释放；插桩的作用和开销；主机时间与 GPU 时间不同 | 画出调用链，定位插桩入口，亲手采集一次短 trace，说明观察到了什么、哪些瓶颈尚未证实 |
| **缓存与调度** | Prefix 复用条件、冷热判定、零引用块淘汰、共享与取消；长度排序和老化；native/cache/scheduler/both 四组对照 | 手推一次前缀复用到释放/淘汰的生命周期，解释活动块为何不能淘汰；解释短请求获益与长请求等待增加 |
| **推测解码与蒸馏** | Draft 提议、Target 验证、接受/拒绝与 bonus；滑窗接受率、K 上下限和持有期；教师答案训练、LoRA、接受率口径 | 定位 K 真正改变提议/验证长度的位置；解释“原 Draft fixed → 新 Draft fixed → 新 Draft adaptive”如何分离贡献；说明 472 条合格样本、128 步序列级蒸馏，不混称 logit 蒸馏 |
| **AWQ 量化** | W4A16、scale/zero point、group size、校准与 AWQ 基本思路；通用/领域数据；代表层局部误差；质量、速度、显存取舍 | 串起校准→导出→加载→评测，亲手加载已有量化产物并对比速度/显存/质量；解释领域 group128 的选择及保留的高精度权重；明确复用 AutoAWQ |
| **CUDA 融合** | RoPE 成对旋转、Q/K/V 布局、slot 映射；v1 每 token 一个线程块；线程索引、读写地址与 FP16 舍入；融合和计时方法 | 读懂 v1 核心 kernel，手推一个 token/head 的读写；说明独立数值对照、非法输入检查和 memcheck 的作用；解释减少了什么开销、支持哪些输入 |
| **性能与部署** | FA2、Nsight 时间线、CPU launch 与 GPU 执行；单卡/双副本/TP2；到达率、排队、P99、SLO 和 goodput | 亲手启动服务、压测并调整配置，用 Nsight 采集和定位主要耗时；复算部署比较，说明两卡资源与负载如何控制，以及为什么 TP2 不一定更好 |

**先记住项目的关键取舍：**自然业务中自研缓存没有额外复用；长度调度存在长请求代价；动态 K 无稳定额外收益；AWQ×推测组合更慢；CUDA 是独立原型，未接服务；高到达率下三种部署仍有大量请求未满足预设 SLO。

代码和证据按需从[六线累计讲解](../../docs/stages/S6/README.md)进入；CUDA 当前先读 [v1 核心实现](../../csrc/rope_cache.cu)。无需一次打开所有文件。

## 3. 必修基础：跟随主线补齐

| 基础 | 最低范围与自测方式 |
|---|---|
| **Transformer 与生成** | Q/K/V、Attention、因果掩码、softmax、RoPE、自回归、Prefill/Decode、MHA/MQA/GQA；能写出主要张量形状，解释生成一个新 token 时哪些计算被复用 |
| **KV 与批处理** | Cache 保存什么、为什么不缓存历史 Q、容量公式、PagedAttention 的分页管理与减少浪费、block table、引用计数、continuous batching；能区分 KV 与模型权重、分页管理与 Prefix Cache 复用 |
| **数值与量化** | FP16/BF16/INT8/INT4，量化/反量化、舍入/截断、权重/激活量化，PTQ/QAT 的区别；能算一个简单例子，解释 W4A16 不代表全模型所有数据都用 4bit |
| **GPU 与 C++/CUDA 基础** | 算力/带宽/容量、计算强度、异步执行、launch 开销；grid/block/warp/thread、基本访存、指针/stride；能解释项目 kernel 索引和为什么不能直接用 CPU 时钟计 GPU 耗时 |
| **实验与指标** | TTFT、TPOT、ITL、E2E、吞吐、P99、goodput；开环/闭环、热身/同步、独立重复、消融、对照条件；区分 train/calibration/dev/test，解释最终测试为何不用于调参 |
| **训练与工程** | 交叉熵、反向传播、优化器、LoRA、梯度累积；checkpoint 中模型/优化器/scheduler/RNG 的作用；Python/PyTorch 张量操作、Linux 进程日志、Git 与版本固定 |

三个必须会解释的例子：

- **KV 容量**：忽略分块浪费等额外开销时，每 token 字节数为 `2 × 层数 × KV头数 × head_dim × 每元素字节数`。项目 FP16 Target 为 `2×28×4×128×2 = 57,344 bytes`，不是按 28 个 Q 头计算。
- **TPOT 口径**：项目按单请求 `(末次内容观测时间－首次内容观测时间)/(输出 token 数－1)` 计算，再聚合。推测解码可能一次返回多个 token，因此它不等于逐 token ITL。
- **性能归因**：FlashAttention 主要减少显存读写和中间结果物化；低 batch Decode 常受带宽影响，但须结合负载验证。显存少、接受率高、命中多，都不自动意味着端到端更快。

对 FlashAttention、PagedAttention、投机解码，分别准备“解决什么问题、什么负载下可能有用、何时收益有限”的解释。分页管理可减少 KV 分配浪费，但不自动减少模型权重；推测收益取决于接受率及 Draft/验证成本；短序列、小工作量下的固定开销可能掩盖 Attention 优化收益。量化速度还取决于硬件、后端算子、batch 和输入长度。

算法面试另外准备：数组、哈希、链表、栈队列、二分、堆、树的 DFS/BFS、排序与复杂度分析；更深题型按目标团队补充。

## 4. 简历四组数字：记住口径，能够复算

| 数字 | 对照与结果 | 必须保留的限制 |
|---|---|---|
| **观测 TPOT 约降 18%** | S5 FP16 Target 对蒸馏 Draft 固定 K：16.6617→13.6884ms，约 17.85% | 相同原生 APC，三轮独立重复；收益不能归因于动态 K，TTFT 同时增加 |
| **进程显存约降 56%** | FP16 对领域 group128 AWQ：15900→6988MiB，约 56.05% | 固定 512 个 KV 块；是该实验结束时 nvidia-smi 的进程显存记录，不是峰值或权重大小 |
| **CUDA 约降 18%–31%** | S3 v1 融合对上游分步执行，六种形状约 18.31%–31.08% | FP16 NeoX、Q28/KV4、D128；CUDA Graph/Event 微基准，未计服务端到端收益 |
| **TP2 P99 约降 27%–34%** | 相对双副本，三轮约 34.11%、26.73%、28.06% | 同两卡、自然负载、标称 32 req/s；每配置每轮 256 请求，用户延迟从计划到达算起；属于有限样本尾部观察 |

统一用 `(基线－候选)/基线` 计算下降比例。四组数字来自不同实验配置，不能相加，也不代表所有优化在同一进程中同时开启。32 req/s 是到达率，不是完成吞吐；两张卡实际各报告 49140MiB，未验证物理 24GB 环境。

最终质量可讲：十种配置各 256 条测试、236 条规则正确；这不证明跨模板泛化或真实驾驶安全。项目起止时间、独立开发等个人履历表述按真实经历填写。

查证入口：[S5 时延与部署](../../docs/s5-results.md) · [AWQ 显存](../../docs/awq-results.md) · [S3 CUDA](../../docs/s3-stability.md) · [最终结果与边界](../../docs/final-report.md)。

## 5. 实操准备：先跑通，再比较，再解释

以下都是待完成任务，不能因文档生成而记作通过。第一轮目标是建立真实操作经验，不要求重演 S1–S6 全部实验或复现原来的提升百分比。

### 5.1 开始前准备

- 确认实际操作机器、代码版本、Python/torch/vLLM 环境、模型目录、GPU/显存、服务端口和已有进程。沿用项目固定环境与资产，先确认哪些已经可用，避免重复启动。原报告中的 `/hy-tmp/...` 是原实例路径，不能直接当作当前机器路径。
- 按[运行清单第0节](interview-benchmark-commands.md)在当前项目切换到 `interview-practice` 学习分支；正式脚本要求干净源码时，先检查并提交自己的源码改动，不删除未提交材料、不绕过证据校验。个人笔记、配置副本和新输出保存在 `artifacts/learning`，记录来源与代码版本；切换分支前停止运行中的任务。
- 使用开发集的小样本；性能比较固定模型、输入、生成参数、热身和缓存起点，每次只改变目标变量。带 profiler 的诊断与正式速度计时分开。新硬件上需重测自己的基线。
- 暂无 GPU 时，可先完成源码阅读、旧 trace 分析和 CPU 复算，GPU 操作保持待完成。[快速开始](../../docs/quickstart.md)的 `demo` 是规则评分演示，复算脚本只读取历史输出；二者都不能算亲手完成了真实模型推理。

### 5.2 第一轮：走通完整的小流程

每步先操作、观察，再回看原理和代码。每次只打开当前需要的一两个入口；具体命令依据实际环境、脚本参数和配置生成，理解后亲手执行。

| 步骤 | 亲手完成的任务 | 观察什么／完成标准 |
|---|---|---|
| **1. 启动与停止服务** | 参考[服务入口](../../scripts/serve_smoke.py)启动 FP16 Target；确认服务就绪，再正常停止自己启动的服务 | 能指出模型目录、设备、端口和日志位置，辨认模型加载、KV 分配与就绪信息；知道如何核对进程退出和显存释放 |
| **2. 发出真实请求** | 用 curl 或 Python 调用模型列表和 chat 接口，分别查看普通与流式响应；改变一次输入或输出长度限制 | 能解释模型名、messages、生成参数、SSE；区分接口外层 JSON 与模型生成的业务 JSON，找到响应、token 数和结束原因 |
| **3. 小规模压测** | 按[开环脚本](../../scripts/benchmark_openloop.py)和原协议制作小规模学习配置，先低负载，再提高一个负载参数 | 能区分客户端并发上限、到达率和服务并发上限；找到逐请求记录，计算 TTFT/TPOT/吞吐，保留失败和超时；小样本 P99 仅作演示 |
| **4. 调整资源配置** | 分别理解 `max_model_len`、`max_num_seqs`、`gpu_memory_utilization`；选择一项做匹配对照 | 能解释预期影响，并从启动日志、实际 KV 块数、显存和延迟核对；知道自动 KV 预算与固定块数实验不同，不为练习故意制造大规模 OOM |
| **5. 采集并分析性能** | 依据[诊断入口](../../docs/engine-diagnostics.md)，用 Nsight Systems 完成一次热身后的短采集，保存并打开自己的 `.nsys-rep` | 能辨认 NVTX、CPU/CUDA API、GPU kernel，用时间线和统计表定位主要耗时；说出一个观测、一项尚未证实的原因及下一步验证 |
| **6. 做优化对照** | 使用[已验证配置](../../configs/final-profiles.json)中的 FP16 Target 与领域 AWQ Target，小规模运行相同输入，分别记录资源、速度和规则质量 | 能核对实际加载的模型/量化后端；说明 KV 预算、输出长度和显存口径；加载已有 AWQ 产物不等于本轮重新做过校准 |
| **7. 回看源码并复述** | 选择刚观察到的一个现象，沿相关入口找到核心实现，并说明下一步会怎样改参数验证 | 能讲清“操作→现象→相关实现→证据与解释”，不把一段日志直接当作完整因果证明 |

**性能工具先练 Nsight Systems 一种即可。** 不只阅读旧截图：应亲自完成采集、报告打开、主要耗时定位和结论解释。kernel 累计时间不一定等于墙钟时间，CPU API 与 GPU 可重叠；kernel 间隙不等于整卡空闲。Nsight Systems 时间线也不足以单独证明某个 kernel 已达到显存带宽上限。PyTorch Profiler 可按需补充，不另设第二套必修操作。

### 5.3 第二轮：补上简历各条的专项体验

| 专项 | 最小操作与要能回答的问题 |
|---|---|
| **缓存与调度** | 用项目既有压力入口运行 native/cache/scheduler/both，查看热点复用、长短请求等待及一项生命周期检查；解释为什么自然业务没有额外命中也可能是正常结果。入口见[缓存调度说明](../../docs/cache-scheduler.md) |
| **推测解码** | 用同一已训练 Draft 比较 Target/fixed/adaptive，查看实际 K 轨迹、接受率和输出核对；再结合原/新 Draft 固定 K 的证据讲清蒸馏贡献。速度比较关闭诊断 trace，K 轨迹另采。入口见[推测说明](../../docs/speculation.md) |
| **独立 CUDA** | 亲手编译并运行 v1 数值检查、一次 Event 微基准及小规模 memcheck，区分编译/热身/检查和正式计时；能指出输出文件、支持形状和未接入服务的边界。入口见[算子说明](../../docs/rope-cache.md) |
| **FA2 与两卡部署** | 运行一次既有 FA2 Prefill 对照；两卡可用时，用相同小负载体验单卡/双副本/TP2 启动和结果。能解释设备、模型副本/切分和请求路由；未亲手执行的配置标记为仅已读历史证据。入口见[FA2 说明](../../docs/fa2-prefill.md)和[部署兼容范围](../../docs/s5-compatibility.md) |

各专项使用项目已验证的独立 profile，不默认将自研策略、推测与 TP2 全部组合。同步引擎实验也不等于 HTTP 服务压测，介绍操作时说明执行路径。

**训练和重新校准可安排在后续专项。** 先核对教师数据、训练日志/checkpoint、AWQ 校准配置/产物及加载链路，确保能解释输入输出和实际贡献。随后按[训练协议](../../docs/distillation-protocol.md)在新输出目录做短训练/恢复体验；需补校准操作时再按[量化协议](../../docs/awq-protocol.md)运行一组。现有 AWQ 脚本固定了校准数据规模和部分路径，不是任意减少步数的通用玩具脚本。第一轮无需重训 128 步或重做全部校准组；未亲手做过的环节，明确区分读过记录、操作过已有产物和本次重新执行。

### 5.4 保留的小型编码与复算练习

- [ ] 用 PyTorch 写简单 causal attention，比较带 KV Cache 的逐步结果与完整前向结果；解释掩码、形状和误差容限。
- [ ] 用 Python 实现简化冷热淘汰或滑窗 K 控制器，覆盖正常与边界情况；说明时间/空间复杂度。
- [ ] 从一份原始记录复算 TPOT 或 P99，再复算四组简历百分比；讲清分母、聚合顺序与比较条件。
- [ ] 手推 v1 CUDA 中一个 token/head 的地址，解释为什么写槽需要互异、哪些输入要拒绝，以及未写槽如何验证。
- [ ] 独立修改一个小逻辑或参数，说明受影响的行为及应补的检查；涉及 GPU 执行的改动没有实测前不称已验证。

### 5.5 每次只留一份简短操作记录

记录以下六项即可，链接原日志和产物，不复制整份输出：

1. **目的与输入**：本次想验证什么，使用哪份模型、数据和代码版本。
2. **操作与参数**：实际命令/配置，关键参数含义，唯一改变的变量。
3. **观察与产物**：日志、请求结果、显存、性能表或 trace 在哪里。
4. **问题与处理**：实际遇到的报错、如何定位、怎样确认恢复；没有报错就如实记录，不编造排障经历。
5. **结论与限制**：看到了什么，哪些解释有证据，下一步会怎么验证。
6. **个人状态**：仅看过演示／在提示下完成／能查文档独立完成；不能把辅助执行直接标为独立掌握。

面试时按这六项还原经历，可以展示关键命令，但不靠背工具名代替操作理解。

## 6. JD 广度与可后置内容

**广度最低要求：能解释“解决什么问题、基本方法、主要代价、适用条件”，无需每项重新做项目。**

| 主题 | 至少需要知道 |
|---|---|
| GPTQ / AWQ / SmoothQuant | 处理的量化误差、使用的校准信息及方法差异；AWQ 结合项目深入，另外两种先能比较 |
| PTQ / QAT | 概念属于第 3 节必修；QAT 完整训练实操可后置，仍须能比较数据与计算成本、适用场景 |
| 剪枝 / 稀疏化 | 结构化与非结构化的区别；参数减少或出现零值为什么未必带来硬件加速 |
| 蒸馏 / NAS | 序列、logit、特征蒸馏的信号差异；NAS 的搜索空间、质量/延迟目标与搜索成本 |
| SGLang / TensorRT-LLM | 与 vLLM 的大致定位、生态和选型因素；不要求三个框架都读源码 |
| 多卡 / MoE / Diffusion | TP 与多副本、all-reduce、PCIe/NVLink 的基本影响；MoE 路由/通信与 Diffusion 多步迭代的成本特点 |

**暂可后置：**vLLM 全仓库及全部 V1 路径、手写 FlashAttention/PagedAttention GPU kernel、CUTLASS/PTX/SASS、复杂 Tensor Core 优化、完整 S4 三堆维护和 CUDA v2 tile/half2 消融、大规模集群运维，以及其余压缩方法的完整实操。

当前简历的 CUDA 数字由 v1 支撑，先讲透 v1；主动把 v2 或堆索引作为亮点介绍时，再提高准备深度。对未实操方法明确说明了解原理即可。

## 7. 面试前自查

- [ ] 能脱稿用两三分钟介绍项目，讲清模型/引擎分工、个人增量和任务边界。
- [ ] 六条简历各能讲清问题、做法、证据、限制，并回答核心追问。
- [ ] 能查文档独立启动/停止服务、发请求、找到日志与输出，解释关键启动和生成参数。
- [ ] 能完成一次小规模压测和单变量调参，说明对照条件、失败分母及延迟/吞吐变化。
- [ ] 亲手完成一次 Nsight 短采集并分析自己的报告，区分主要耗时的观测、瓶颈假设与后续验证。
- [ ] 亲手加载 FP16/AWQ 做资源、速度和质量对照，并按第 5.3 节完成专项体验；缺少条件的实操保持待完成。
- [ ] 能定位各条关键代码，解释输入、状态变化、输出，以及一项正确性检查。
- [ ] 能复算四组数字，不混淆固定 K/动态 K、权重/进程显存、微基准/服务收益、到达率/吞吐。
- [ ] 能完成上述小练习与基础编码题，对“换一个条件会怎样”给出有依据的分析。
- [ ] 能区分实测结论、合理推测和未验证事项；完成必修知识，广度概念不混淆。

自查按“**能解释、能操作、能判断结果**”分别核验；看过报告不替代操作，命令成功退出也不替代结果核对。达成这些是本指南的最低准备目标，不等于企业录用保证。需要深入时再查[累计学习核验](../../docs/learning-guide.md)和[六线累计讲解](../../docs/stages/S6/README.md)；自己的新练习按[运行清单](interview-benchmark-commands.md)末尾模板记录。
