# S2 匹配 HTTP 部署对照

> S3更新：三轮部署、TP2性能波动与质量差异已完成，见[独立重复](s3-stability.md)、[边界报告](../reports/s3-boundaries.json)和[S3累计讲解](stages/S3/README.md)。下文保留S2实现与初测来源，不把旧单次结果混成S3计时。

单卡、双副本和TP2实际各跑256请求，共768/768完成，无失败/超时。各配置每单元64 dev请求，prompt512/1536、global concurrency1/8；原始SSE、服务日志、计时和重聚合见 [报告](../reports/s2-deployments.json)。一次运行的小样本不代表稳定尾延迟或正式SLO。

## 配置与公平范围

固定FP16 Qwen2.5-7B、vLLM0.8.5 V0、FA2、CUDA Graph，APC/chunked均显式关闭，context2048、max_batched_tokens2048、每卡总显存比例0.45。单卡GPU0/maxseq8；双副本GPU0/1各maxseq4，按索引轮询；TP2用两卡/global maxseq8。双卡预算匹配，单卡单独计每卡效率；没有约束相同总KV槽位。每单元4条顺序热身，测量64条闭环请求，无固定到达率。

两卡无NVLink、P2P失败且custom all-reduce关闭；不能仅凭拓扑推定TP2必慢。服务启动、Graph捕获和热身在测量外。CPU后台OSS仅在部分单元继续，独占GPU但未隔离CPU/I/O；S3另做无备份独立重复。

## 观测、建议与限制

并发1时，TP2在512token下69.55token/s、双副本53.80，前者E2E P50更小但TTFT更大；1536token下44.69与42.00，差距更小。并发1无法同时填满双副本，两卡资源不自动转成两倍并行。单卡每卡效率在本矩阵中优于把并发1分到两卡，容量足够且请求稀疏时保留单卡。

并发8时，512token双副本284.49/TP2 174.32，比例1.632；1536token163.05/71.64，比例2.276，双副本TTFT和E2E也较低。这支持高并发时先考虑副本扩展的探索性建议，不能凭一次run写稳定63%/128%加速。单卡在512并发8为207.13token/s/GPU，双副本142.24/GPU；总吞吐和成本效率是不同选择。

在所有512单元，三部署文本逐请求完全相同且58/64规则正确。1536单元，单卡/副本均44/64；TP2均43/64，同一dev-030由stop/stopped/true变为proceed/road_limit/false，两个并发配置重现。完整输入与输出差异保留在output_comparisons。尚未采同前缀logprob定位，不把它未经证实地归因为归约误差；TP2不作为保持逐条质量的默认替换。

长度来自在chat之前填充background token，属于合成压力，1536时连FP16基线也明显降质，不代表真实长场景任务效果。不能把单元成功率100%等同业务正确率，也不能只按token/s忽略较低质量。S3须复查该差异、重复计时和服务基线；S5再用最终冻结测试与部署条件验收。
