## 从零到现在

原目录只有五个规范文件，没有 Git 或代码。现在 main 管理可安装的 Python 包、128 条规则场景、测试、固定上游/模型引用和真实运行记录；GitHub 首次推送成功。真实模型服务、TP2、固定 K、CUDA Graph 可运行；工程尚未进入六线优化结果阶段。

一次 CPU 示例从 `task.generate` 建立场景及 group_id，`validate_scene` 检查字段，`messages` 去除 ID 后构建输入，`label` 按 stop/slow/proceed 规则产生独立真值，`score` 严格检查输出 JSON。规则 demo 直接调用 label；真实客户端会调用独立服务，因此两者证据严格区分。

一次客户端请求经过 `benchmark.request` 的 HTTP POST、SSE 消费、非空内容计时、服务端 usage 记录与评分。`aggregate` 在成功请求上计算 nearest-rank 分位数，同时保留所有尝试的失败率和质量分母。chunk 不是 token，不能由这些样例声称逐 token ITL 或 Decode kernel 时间。

`Run` 在启动时保存代码 SHA、dirty 状态、环境、配置与进程身份，结束时保存资产 hash。探索性 dirty 运行还保存源码快照。正式运行需要提交和 clean 工作树；小型最终证据显式加入 Git，活动日志不让源码变脏。中断任务用 checkpoint+flock 恢复，不能将两段 benchmark 拼接成一次性能成绩。

## 决策、失败与实验解释

见 `docs/decisions/0001-foundation.md` 和进度中的失败记录。关键例子是终止 pip 父进程不一定终止孙进程；日志因此在摘要后变化。保存旧 hash 与原因，修复进程组监督后，再执行可验证的退出测试。这个案例说明进程退出、任务完成与证据封存必须分别检查。

CPU 测试的成功数证明相应输入边界、协议处理和记录机制；它不证明任务模型准确率。GPU matmul 证明设备可执行简单算术；实际服务成功另有客户端记录。TP2 日志表明 P2P 不可用，不能因双卡启动成功推断高效通信。当前没有任何 15%、18%、68%、55%、20% 的实测收益。

复现命令与指标边界见 `docs/reproduce.md`。所有 run 的 code.sha 是运行时提交，而不是之后提交报告的 SHA。

## 真实服务结果的解释

单卡、TP2 和固定 K 的 32 条开发样例都成功返回，JSON 有效率 32/32，全字段正确 31/32。唯一失败样例 speed=24.134m/s、lead=21.104m，规则应 slow，模型答 proceed。该错误保留，不用教师输出替换独立标签。固定 K 与普通贪心文本 32/32 相同不等于业务 100% 正确。

固定 K 派生导出只给 tied embedding 增加 128 行零值，原 338 个张量已有值逐项不变，Target 不变。零行改变 Draft softmax 的归一化，不代表原 Draft 分布不变；上游拒绝采样逻辑仍保留。详见 ADR 0002 和 reports/s1-fixed-k-smoke.json。

CUDA Graph 服务 run `20261014T222511+0800-4cb3e5f58b` 日志记录捕获 batch 1/2/4；客户端 `20261014T222651+0800-fb80024005` 为 32/32 成功、31/32 正确。运行时工作树为 dirty，快照已保存，这是探索性兼容检查，不能升级为正式性能成绩。这里验证的是 V0 CUDA Graph，没有宣称 torch.compile 或所有动态图路径通过。

服务验证后主动 SIGTERM，manifest 的 interrupted 表示受控停止；请求成功应看关联客户端，不能把服务器正常退出或被停止直接视为推理失败或成功。
